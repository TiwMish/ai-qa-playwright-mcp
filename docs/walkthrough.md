# Walkthrough — understanding this project in 30 minutes

This guide explains the whole project in reading order. If you can explain
each numbered step out loud, you can talk about this project confidently
in an interview.

## The one-sentence version

A Playwright (TypeScript) test suite for a demo to-do app, built to show
three practical ways AI helps a QA engineer: **designing tests, exploring
with an agent (MCP), and triaging failures** — while the committed tests
themselves stay 100% deterministic (no AI calls when tests run).

## Step 1 — Run it (5 minutes)

```bash
npm install
npx playwright install chromium
npm test
```

You should see **8 tests pass**. Then run `npm run test:ui` and click
through a test — UI mode shows you every step, the page at each step,
and the locator used. This is the fastest way to *see* what the suite does.

What is being tested? **TodoMVC** (https://demo.playwright.dev/todomvc),
a small to-do list app: add tasks, tick them off, filter All/Active/
Completed, clear completed, and tasks survive a page reload. Small app,
real behaviours.

## Step 2 — The map (what each folder is for)

| Path | What it is |
|---|---|
| `tests/todo.spec.ts` | The regression suite — 6 tests, TC-01 … TC-06 |
| `tests/ai-assisted/self-healing.spec.ts` | 2 tests demonstrating AI-era patterns (semantic locators, AI-generated bulk data) |
| `tests/pages/TodoPage.ts` | A **Page Object**: one class that knows how to operate the app, so tests read like plain English |
| `fixtures/test-data.ts` | The test data, including a list **generated by GitHub Copilot** |
| `playwright.config.ts` | Runner settings: which site, which browsers, screenshots/traces on failure |
| `ai/requirements/` | A sample user story — the *input* to AI test design |
| `ai/prompts/` | The two prompt templates (test-case generation, failure triage) |
| `ai/examples/` | The AI-generated test cases, reviewed by a human — TC-01…TC-09 |
| `.vscode/mcp.json` | MCP server configuration (Playwright + GitHub) for VS Code |
| `docs/mcp-with-playwright.md` | The MCP explainer: servers, clients, MCP vs APIs |
| `.github/workflows/playwright.yml` | CI: GitHub runs the suite on every push |

## Step 3 — Read the code in this order (10 minutes)

1. **`tests/todo.spec.ts`** — start here. Each test is short because it
   delegates to the Page Object: `todo.addTodo(...)`,
   `todo.expectCount(2)`. Notice the test IDs (TC-01…) — they match the
   table in `ai/examples/generated-test-cases.md`. That traceability
   (story → AI-drafted cases → automated tests) is the design story.
2. **`tests/pages/TodoPage.ts`** — look at *how* elements are found:
   `getByPlaceholder('What needs to be done?')`, `getByRole('button',
   { name: 'Clear completed' })`. These are **semantic locators** — they
   describe what a user sees. No XPath, no CSS class chains. If the
   developers restyle the page, these still work; that resilience is
   what "self-healing-friendly" means. It's also exactly the information
   an AI agent gets from the accessibility tree via MCP — humans and
   agents share one vocabulary for the page.
3. **`playwright.config.ts`** — note `baseURL` (overridable with the
   `BASE_URL` env var), the three browser projects, and
   screenshot/trace **on failure only** — the evidence the triage
   workflow consumes.

## Step 4 — The three AI workflows (the actual point of the project)

**1. AI test design.** `ai/prompts/test-case-generation.md` is a prompt
that turns a user story into a table of test cases with steps and
expected results, and forces the AI to flag ambiguous requirements.
`ai/examples/generated-test-cases.md` is real output for the story in
`ai/requirements/`: 9 cases — 6 automated, 3 left exploratory (empty
input, duplicates, very long text) — plus two questions the AI raised
for the product owner. *The QA engineer reviews and decides; the AI
drafts.* That division of labour is the interview answer.

**2. Agent exploration via MCP.** With `.vscode/mcp.json`, VS Code can
start Microsoft's Playwright MCP server. An AI agent (Copilot/Claude)
then receives tools like `browser_navigate`, `browser_snapshot`,
`browser_click`. It reads the page as an **accessibility-tree snapshot**
— a structured list of elements with names and references — decides
what to do, acts, and re-reads. You can ask it to perform a flow and
then *write the Playwright test for it* using the existing Page Object.
Full explainer: `docs/mcp-with-playwright.md`.

**3. AI failure triage.** When a test fails in CI you get an error, a
screenshot and a trace. `ai/prompts/failure-triage.md` is a prompt that
turns those into a structured first hypothesis: what was intended, what
happened, likely category (product defect / test defect / environment /
flaky) with confidence, and the single next debugging step. Minutes
instead of an hour — with a human confirming before any fix.

*Real example from this repo:* the first CI run failed all 8 tests. The
error was a navigation mistake — tests went to the site root instead of
the `/todomvc/` path inside the base URL. Fixed by navigating relative
to the base URL; CI went green. That fix is in the git history
(commit "Fix navigation…"), and it's a good story: the pipeline caught
what a local run against a root-served copy could not.

## Step 5 — Say it in an interview (2-minute script)

> "I built a small Playwright-TypeScript framework to practise AI-assisted
> QA the way I'd use it on a real team. The AI works at the edges: it
> drafts test cases from user stories using a prompt template I wrote —
> I review them, and the approved cases become automated tests with
> full traceability. I use Copilot for framework code and bulk test
> data. For exploration, I connect an agent to the browser through the
> Playwright MCP server — it works from accessibility snapshots, which
> is why my framework uses semantic locators everywhere. When CI fails,
> I use a triage prompt to get a root-cause hypothesis from the trace
> before I debug. The regression suite itself is deterministic — no
> LLM in the test run — because CI has to be trustworthy."

## Step 6 — Try breaking it (best learning exercise)

1. Change a locator in `TodoPage.ts` to a wrong placeholder and run
   `npm test` — watch it fail, open the HTML report (`npm run report`),
   and find the error context and screenshot.
2. Add a 7th test to `todo.spec.ts` for TC-08 (duplicate todos) using
   the Page Object — three or four lines.
3. In VS Code, start the Playwright MCP server from `.vscode/mcp.json`
   and ask Copilot (Agent mode) to add a task in the demo app.
